# Мастерская APK и подпись IPA

Мастерская хранит исходный APK отдельно от разобранных Manifest, ресурсов и Smali. Изменение Java-псевдокода не является пересборкой DEX: меняйте Smali или ресурсы. Планы правок проверяют исходный SHA-256 и применяются отдельной командой; доступны отмена и повтор.

Разбор создаёт собственный снимок текущего архива. Последующие правки в обычном дереве проекта не переносятся в этот снимок автоматически: мастерская предупреждает, если исходное дерево изменилось. Повторный вызов «Разобрать» сохраняет существующую мастерскую. Для нового разбора импортируйте APK отдельным проектом.

## Android

Нужны JDK, Apktool, zipalign и apksigner. Для создания ключа — keytool из JDK. Выберите инструменты в настройках; Apktool поддерживает путь к `.jar`. SDK Build Tools содержат zipalign и apksigner. Скачивание внутри приложения не выполняется автоматически.

Порядок сборки:

1. Материализация проверенных снимков в временную папку.
2. Apktool компилирует Smali и ресурсы.
3. Проверка APK/CRC и zipalign с выравниванием несжатых `.so` на 16 КиБ.
4. При выбранном ключе — apksigner и повторная проверка подписи/выравнивания.
5. Создание нового выходного файла после успешных проверок.

Существующий файл не перезаписывается. Ошибка подписи не выдаёт файл со статусом «подписан». Без выбранного ключа возможна сборка с явным статусом `requires_signing`.

Пароли используются только во время операции и передаются дочернему процессу через переменные окружения, не через аргументы команд. В проект, историю и рецепт они не сохраняются. Созданный PKCS12 хранится только по явно выбранному пути с правами `0600`; сохраните его и пароль самостоятельно. Импорт существующего keystore — выбор файла и проверка его публичных сертификатов, без копирования закрытого ключа в проект.

Для обновления установленного приложения обычно нужен исходный ключ подписи. Другой ключ не делает модифицированный APK совместимым обновлением оригинала. Помимо zipalign выдаётся отдельный отчёт `native_alignment` по PT_LOAD/GNU_RELRO внутри `.so`. Эти сегменты автоматически не переписываются; установка и выполнение требуют отдельной проверки.

Официальные источники: [Apktool CLI](https://apktool.org/docs/cli-parameters/), [Android apksigner](https://developer.android.com/tools/apksigner), [Android zipalign](https://developer.android.com/tools/zipalign).

## APK-наборы и AAB

Откройте `.apks`, `.xapk` или `.apkm` как отдельный проект. Раздел комплектов показывает входящие APK, package name, версию, основной APK и зависимости сплитов. Выбранную часть можно открыть как самостоятельный APK-проект. Одна часть набора часто недостаточна для установки: основной APK, модули и конфигурационные сплиты должны соответствовать друг другу.

Для AAB выберите bundletool — исполняемый файл или официальный `.jar` — и Java в «Инструментах». В разделе комплектов укажите собственный keystore, alias и пароль, затем выберите режим:

- **Universal:** один APK с модулями, допускающими объединение. Некоторые динамические модули могут не войти в него.
- **Default:** набор APK для разных конфигураций устройств. Он не означает, что нужно установить все конфигурации одновременно.

Выберите выходной `.apks`. После сборки приложение проверяет архив и подпись каждой части через apksigner. Этот результат ещё не подтверждает установку или запуск. Исходный AAB сохраняется.

В адаптере bundletool пароли передаются через анонимные временные файлы с правами `0600` и наследуемые дескрипторы. В проект и историю они не сохраняются; именованные файлы с паролями не остаются при отмене операции. Для результата нужен новый путь: существующий `.apks` не перезаписывается.

Официальная документация: [bundletool](https://developer.android.com/tools/bundletool).

## Android-устройство: только по нажатию

Эти действия необязательны и не запускаются при открытии проекта. Установите [Android SDK Platform Tools](https://developer.android.com/tools/releases/platform-tools), выберите `adb` в «Инструментах», включите USB-отладку на своём Android и подтвердите подключение на устройстве.

1. Откройте раздел Android-устройства и нажмите получение списка. Выберите конкретное устройство со статусом `device`; при `unauthorized` сначала разрешите USB-отладку на самом Android.
2. По отдельной кнопке получите список сторонних приложений. Импорт установленного приложения копирует его APK и сплиты в новый проект. Приватные данные приложения и OBB не копируются.
3. Для установки выберите подписанный APK или совместимые APK одного набора. Программа проверяет package name, версии, подписи и объявленные зависимости. Обновление существующего приложения включается отдельно; несовместимый ключ не заменяется автоматически.
4. Запуск установленного приложения выполняется отдельной кнопкой. Подтверждение запуска Activity не является проверкой всех функций.
5. После запуска можно вручную прочитать последние сообщения logcat выбранного процесса. Журнал очищается от типовых секретов; автоматическое наблюдение не включается.

Приложение не удаляет установленные приложения, не выполняет автоматическое сопряжение и не управляет экраном устройства. При ошибке установки исходный файл остаётся доступен; исправляйте причину по сообщению Android, не подменяя статус «проверен» статусом «установлен».

## iOS

Переподпись IPA — экспериментальный инструмент для macOS. Apple прямо отмечает, что командная переподпись iOS не является поддерживаемым способом дистрибуции. Успешный `codesign verify` не гарантирует установку или запуск на iPhone. [Документация Apple](https://developer.apple.com/documentation/xcode/using-the-latest-code-signature-format).

Нужно явно выбрать:

- identity с сертификатом и закрытым ключом в Keychain — список публичных названий/fingerprint запрашивается только кнопкой выбора сертификата;
- совместимый `.mobileprovision` для каждого `.app` и `.appex`;
- при необходимости отдельный plist entitlements для конкретного Bundle ID.

Проверяются срок профиля, fingerprint разрешённого сертификата, Team ID, Bundle ID и допустимость каждого запрошенного entitlement. Entitlements профиля — разрешения, а не список возможностей, которые нужно автоматически включить. Несовместимые capabilities вызывают ошибку с названием поля. [Apple TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles).

Зашифрованный Mach-O отклоняется: подпись не расшифровывает исполняемый код. Bundle ID не переименовываются, профили не создаются, Apple ID не запрашивается. Вложенный код подписывается от глубоких объектов к родительским; основное приложение — последним. Frameworks подписываются без entitlements и provisioning profiles. Все объекты повторно проверяются, затем создаётся новый IPA.

Локального выполнения iOS-переподписи с действующим пользовательским сертификатом в ходе разработки не проводилось: чужие credentials не использовались. Проверки профилей и отказов покрыты изолированными тестами.

## Windows PE

Для отдельного EXE/DLL/SYS проекта доступен внешний osslsigncode: выберите собственный PFX/PKCS12 и пароль. При необходимости укажите PEM с доверенными CA для проверки, например собственный тестовый сертификат. Выбранный PEM не устанавливается в системное хранилище доверия.

Пароль передаётся через анонимный временный файл `0600`, открытый только по наследуемому дескриптору. Именованного файла с паролем не остаётся даже при остановке worker. После подписи SHA-256 инструмент проверяет Authenticode и цепочку сертификатов. Проверка должна завершиться успешно до выдачи нового файла.

Timestamp не добавляется; получение CRL по сети отключено. Статус означает проверку в явно выбранном или стандартном наборе CA инструмента. Это не гарантия доверия Windows/SmartScreen, пригодности сертификата для драйвера или запуска программы. [Официальный справочник osslsigncode](https://github.com/mtrojnar/osslsigncode/blob/master/osslsigncode.md).

## Статусы и проверка разработки

`assembled` означает успешную сборку архива; `signature_verified` — успешную проверку подписи инструментом. `runtime_status: untested` сохраняется до отдельной реальной проверки на устройстве. Приложение не выдаёт эти статусы за установку, запуск или проверку всех функций.

Реально проверен полный Android-проход на собственном учебном приложении: JDK + SDK 35 aapt2/D8 → импорт APK → Apktool 3.0.3 → изменение инструкции Smali (`timeout()` возвращает 7 вместо 3) → сборка → zipalign → собственный тестовый PKCS12 → apksigner. Схемы v1/v2/v3 успешно проверены. Повторный разбор подписанного APK подтвердил изменённую инструкцию. Устройство не подключалось.

Архив Apktool проверен по SHA-256 из официального релиза GitHub; Android SDK Build Tools и платформа — по опубликованным Google контрольным суммам repository XML.

Также реально проверен osslsigncode 2.14.1: собственный сгенерированный PE подписан собственным краткосрочным тестовым PFX, а SHA-256 Authenticode и цепочка проверены с явно выбранным тестовым CA. PE не запускался.

## RPC

Все методы передаются в обычный `rpc`. Подписывающие методы не включены в список инструментов ИИ.

- `apk_decode {project_id}` → `{workspace_id,status:"decoded",file_count,edit_count,source_changed,warnings}`.
- `apk_workspace_status {project_id}` → состояние; `not_decoded`, если разбора ещё нет.
- `apk_workspace_files {project_id,query?,offset?,limit?}` → `{items:[{path,size,kind,modified,editable}],total}`.
- `apk_workspace_read {project_id,path}` → `{path,size,text?,hex,sha256,truncated,editable}`.
- `apk_workspace_propose {project_id,path,text?|replacement_path?,reason?}` → `{id,path,before_sha256,after_sha256,before_preview,after_preview,status:"validated"}`. Ровно один источник замены; XML/JSON проверяются, `apktool.yml` закрыт для редактирования.
- `apk_workspace_apply {project_id,plan_id}` → состояние. План хранится сервером; перед применением исходный снимок повторно проверяется.
- `apk_workspace_history {project_id}` → массив действий; `data` содержит сериализованный план.
- `apk_workspace_undo {project_id}` / `apk_workspace_redo {project_id}` → состояние.
- `apk_build {project_id,path,sign?:{keystore,alias,store_password,key_password?}}` → результат сборки.
- `keystore_create {path,alias,password,common_name?}` → `{path,alias,certificate}`.
- `keystore_inspect {path,password}` → `{path,aliases,certificate}`.
- `ipa_signing_info {project_id}` → `{bundles:[{path,bundle_id,executable,kind}],encrypted,warnings}`.
- `ipa_identities {}` → `{identities:[{fingerprint,name}],warnings}`; явное действие пользователя.
- `ipa_resign {project_id,path,identity,profiles:[{bundle_id,path}],entitlements?:[{bundle_id,path}]}` → результат сборки; `identity` — SHA-1 выбранного сертификата.
- `pe_sign {project_id,path,pfx,password,ca_file?}` → результат сборки плюс `trust_scope:"selected_ca_file"|"tool_default_ca"`, `timestamped:false`.

Результат сборки: `{path,size,sha256,status,signature_status,runtime_status,checks:[{name,status,message}],warnings,log}`. Журнал ограничен по объёму и очищается от паролей.
